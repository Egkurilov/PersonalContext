# PC-002: внутреннее хранилище сессий владельца

Миграция `0005` добавляет сессии с независимыми случайными 256-битными
значениями session и CSRF. В SQLite хранятся только SHA-256 этих значений,
хеш текущей учётной записи и времена выпуска/истечения. Время жизни — 30 минут;
не более 16 действующих записей. Устаревшие записи удаляются при выдаче новой
сессии, активные сессии при достижении лимита не вытесняются.

`create_session` — внутренний примитив: вызывать его только после успешной
проверки пароля и ограничения частоты. Он повторно сверяет хеш владельца в
`BEGIN IMMEDIATE`, чтобы параллельная смена учётных данных не создала сессию
по устаревшему паролю. Смена хеша владельца делает существующие сессии
недействительными. Logout вызывает `revoke_authorized_session`.
Создание и отзыв проводятся через single-writer; секреты выдаются после commit.

`session_active` проверяет чтение, `authorize_mutation` требует CSRF и уже
открытую транзакцию. Для изменения данных авторизацию и само изменение нужно
выполнить в одном `BEGIN IMMEDIATE` на writer: иначе отзыв может произойти
между проверкой и записью. Для будущых изменяющих API это правило обязательно.

Внутренний `OwnerLogin` учитывает попытку до Argon2, выполняет проверку вне
SQLite и event loop и создаёт сессию только после успеха. При отсутствии или
повреждении хеша он использует временный dummy-хеш того же профиля. Logout
проверяет session и CSRF и удаляет сессию в одной транзакции. Loopback API
предоставляет bootstrap, login, me, csrf и logout: требуется точный Origin для POST,
cookie — HttpOnly, SameSite=Strict, без Secure только на loopback HTTP; CSRF
возвращается при входе в ответе и передаётся заголовком при выходе. Строгие
Host, Origin, схема и peer проверяются middleware, ответы авторизации не
кешируются. `POST /csrf` с проверкой Origin и действующей сессии атомарно
заменяет CSRF, позволяя интерфейсу выполнить выход после обновления страницы;
предыдущий CSRF становится недействительным. Первичная настройка доступна
через локальный диалог трея, вход и выход — через веб-интерфейс. Не логировать
секреты, не помещать их в URL,
DOM или localStorage. Перед миграцией существующей БД создаётся DPAPI backup;
при откате восстановить проверенную копию в новый файл по инструкции README.
Downgrade удаляет сессии и сам по себе не восстанавливает прежние данные.

`POST /api/v1/auth/rotate` требует действующую сессию, текущий CSRF и точный
Origin. В одной транзакции он заменяет хеши обоих случайных секретов и записывает
категорию `owner_session_rotate` без секретов в аудит. Ответ содержит новый CSRF
и новую HttpOnly/SameSite=Strict cookie; прежние значения сразу недействительны.
Срок действия серверной сессии не продлевается. Миграция `0011` расширяет
категории аудита; downgrade с записью о ротации запрещён, для отката используется
проверенная резервная копия. Сетевой HTTPS-вариант Secure cookie ещё не реализован.
